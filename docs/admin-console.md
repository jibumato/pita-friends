# 運営コンソールの使い方

`設定 → 管理者メニュー → 運営コンソール`（`admins` テーブルに登録済みのアカウントのみ）。

0066 で追加しました。**これまで締切のある作業がすべて Supabase の SQL Editor 送り
だったもの**を、アプリの中で片付けられるようにしたものです。

> ⚠️ **判定はDB側にあります。** 画面を隠すだけの制御にはしていません
> （隠しても叩けるなら意味がないため）。すべてのRPCが `NOT_ADMIN` で落ちます。
> 検証は `supabase/tests/73_admin_console.sql`。

---

## タブごとの役目

### やること

件数だけを出します。押すと該当タブへ飛びます。**赤字は放置すると困るもの**です。

| 項目 | 見かたのポイント |
|---|---|
| 保留中の予約 / 保留の最長日数 | **ここが赤いあいだ、ピタメイトの報酬が凍結されています。**14日を超えたら最優先 |
| 未処理の換金申請 | 締めは毎週日曜23:59、支払いは翌週金曜 |
| 未処理の開示・削除請求 | 個人情報保護法の期限があります |
| 整合性の警告 | 0以外なら「健全性」タブで中身を見る |
| プッシュ諦めた件数 | 3回失敗して捨てた分。増え続けるなら配線を疑う |
| 台帳バックアップ経過時間 | **「—」はまだ一度も成功していない**（`workers/ledger-export` 未デプロイ） |

### 保留

申し出や通報で自動確定を止めている予約（0042）。出口は2つです。

- **返還して解除** … 申し出を認める。割合を選ぶ（0/25/50/75/100%）。
  残りはピタメイトの報酬として確定します
- **申し出を退けて確定** … 全額をピタメイトへ

どちらも**理由の入力が必須**です。理由は操作記録に残り、後から
「なぜ50%にしたのか」を説明できるようにしてあります
（判断基準は `docs/refund-claim-policy.md`）。

### 通報

重いものと古いものが上に来ます。通報時のメッセージの抜粋、相手のマナースコア、
**その人への通報の通算件数**（常習かどうかの判断材料）が出ます。

- **違反として処分** / **違反なしで終了** のどちらか
- 減点（0/1/3/5/10）を選ぶとマナースコアに反映されます
- 理由は必須

### トーク（0118）

通報は受け取れるのに、**中身を消す手段がありませんでした。** ここがその手段です。

- 利用者IDでその人のトークを探す（通報タブの「この人のトークを見る」からも来られます）
- スレッドを開くと中身が読める。**開いた事実が操作記録に残ります**（0068 と同じ扱い）
- メッセージ単位で削除。**理由は必須**で、送信者に理由つきの通知が飛びます（規約 第10条の2 6項）

削除の仕組み:

| | どうなるか |
|---|---|
| 行 | 消えません（`deleted_at` が立つ）。通報の裏取りに要るため |
| 本文 | **DBから消えます。** 原文は `message_deletions`（運営のみ）へ移ります |
| 相手の画面 | 「このメッセージは運営が削除しました」に変わります（黙って消しません） |
| 受け取った側への通知 | 飛びません（運営の判断の内容を第三者に配らない） |

> **本文をDBから消しているのは、画面で隠すだけでは足りないからです。**
> トーク画面が読む select は `body` をそのまま取るので、`deleted_at` を
> 立てるだけだと本文は相手のクライアントに届き続けます。
> 「削除済みなら本文が空」は CHECK 制約で強制しているので、
> 実装の抜けで本文が残ることはありません。

### 募集（0112）

不適切な募集投稿を取り下げます。**通報は「人」に対するもので投稿を指せない**ため、
このタブが無いと、見つけても SQL Editor でしか消せませんでした（突合表 G21）。

募集板は `0113` から「**ピタメイトが空き枠を告知して、ゲストを呼ぶ場**」です。
投稿できるのは本人確認を済ませたピタメイトだけで、ゲストの操作は
**予約の申込み**（無料で参加する経路はありません）。

- 既定は**募集中**だけ。「すべて」に切り替えると取り下げ済みも見えます
  （消したはずのものが消えているかを確かめる場所でもあります）
- **理由は必須**。規約 第10条の2 6項が「削除の理由をユーザーに通知します」と
  定めているので、入力した理由が**そのまま投稿者に届きます**
- この募集から予約を申し込んでいたゲストには、**理由を伏せて**「取り下げられた」ことだけ伝わります（運営の判断の内容を第三者に配らないため）
- **予約は取り消されません。** 予約のキャンセルは規約 第9条の返金の規定に乗るので、
  板の都合で消しません。必要なら別途対応します
- **投稿は削除しません。** `status = cancelled` にして残します。通報の裏取りに要ります

### 換金

> ⚠️ **弁護士の確認が済むまで、実際の銀行振込は行わないでください。**
> 申請は溜めておいて構いません（報酬コインは失効しません）。
> この画面は申請の確認とCSV出力までを担います。

- **CSVをダウンロード** … 銀行の一括振込に貼れる形（BOM付きなのでExcelで開けます）
- **本人確認が未完了の申請には赤い警告**が出ます。振り込まないでください
- **振込済みにする** は**実際に振り込んだ後の記録**です。取り消せません
- **振込失敗（全額戻す）** は手数料も含めて申請コインが全額戻ります（0014）

**この一覧を開いたこと自体が操作記録に残ります**（誰がいつ口座情報を見たか）。
口座情報はこのシステムでいちばん機微な情報なので、あえてそうしています。

### 請求

開示・削除請求。10日を超えると赤くなります。

> ⚠️ **削除請求で実際にデータを匿名化するのは `anonymize_user()`（0046）です。**
> ここで「対応済み」にしてもデータは消えません。取り違えると復旧できないので、
> 匿名化を実行してから押してください（手順は `docs/data-integrity.md`）。

### 制限値（0101）

**規約に数値が書かれていない制限**をここから動かします。規約は「一定期間」
「最長30日」という幅だけを定め、具体的な数値は運営が変更できる建て付けにして
あります（第7条の2・第8条の6第5項）。**だから料率と違って告知期間は要りません。**

| 分類 | 項目 |
|---|---|
| 新規ユーザー（第8条の6第5項） | 新規とみなす期間 / 1回あたりの購入上限 / 期間中の購入上限 / 換金の保留 |
| ありがとうギフト（第7条の2） | 1回あたり / 送り主24時間 / 送り主30日 / 受け取る側30日 / 同じ相手30日 / 完了から贈れる期間 |

変更には**理由が必須**で、`giftMaxPerTx: 50000→500 理由: …` の形で前後の値ごと
操作記録に残ります。**後から「理由なく上限を下げて換金させなかった」と言われた
ときの反証材料はこれだけです。**

#### 天井（変えられない上限）

各項目には CHECK 制約で天井が置いてあり、画面にも「上限 ◯◯」と出ます。
超える値を入れると保存できません。

- **換金の保留 30日** … 規約が「最長30日間」と明記しているため
- **ギフトの各上限** … ギフトを「プレイへの謝礼」の範囲に留めるための線
  （為替取引に当たらないという整理の一部）
- **完了から贈れる期間 90日** … これを超えると「完了した役務への謝礼」という
  牽連性の説明が苦しくなる

> ⚠️ **天井そのものを上げるのは弁護士に相談してから。** 天井は
> `supabase/migrations/0101_operator_adjustable_limits.sql` の CHECK 制約にあり、
> `admin_platform_limits()` が同じ値を `caps` として返しています。**片方だけ直すと
> 画面が嘘をつきます。**

#### ここに無いもの

ギフトの「相手はプレイした人に限る」「贈り合いの禁止」「原資は購入コインのみ」
「チャージから24時間は贈れない」「受け取りから7日は換金できない」は**数値ではない**
ので、この画面にはありません。緩める判断は弁護士に相談してから
（`supabase/tests/89_gift_legal_invariants.sql` が固定しています）。

換金の最低申請額（5,000）と換金事務手数料（300）も入れていません。特商法表記・
ウォレット画面・利用規約に**数値そのものが書かれている**ため、変えるなら書面の
改定とセットになります。表だけ動かせるようにすると、画面の数字と実際の挙動が
ずれる事故になります。

### 異議申立て — 証跡を出す（0106）

各カードの下に **「証跡を出す」** があります。押すと、Stripeの申立てフォームの
欄立てに合わせた一式が表示され、クリップボードにもコピーされます。

**Stripeの反論期限は短いので、その場でSQLを書く運用は成立しません。**
1回押して、フォームに写してください。

含まれるもの: 本人確認の結果・使ったカード（ブランド／下4桁）・**購入時点のIPと
端末とブラウザ**・請求の内訳・**同意した日時とそのとき表示していた文面**・
予約ごとの双方のチェックイン時刻と完了時刻・ログイン記録。

> ⚠️ **メッセージの本文は含まれません。** 第三者（ピタメイト）の発言が混ざるため、
> 提出するかどうかは個人情報の第三者提供として別に判断してください。

> ⚠️ **`available: false`** は「IPが空だった」ではなく「**記録していなかった**」
> という意味です（0106より前の購入）。公開後にこれが出るなら、
> `create-checkout-session` の記録が効いていません。

### 経営（0105）

**事業計画書（`business-plan-2026-08.md`）が置いた前提が、実績とずれていないか**を見る
だけの画面です。ここで判断はしません。3つあります。

| 指標 | 見かた | 割ったら |
|---|---|---|
| **① 混合実効率** | 計画の**18%**と比べるのは「予約だけ」。ギフトは一律35%なので、合算は上に引っぱられる | **16%を切ったら**段の見直しを検討（「料率」タブから30日前に予告） |
| **② 上位への集中** | 上位5人・最大1人が予約GMVに占める割合。**最大の1人が抜けたら売上のその割合が消える** | 60%超で赤。超過累進なので①の下振れの原因にもなる |
| **③ チャージバック** | 分母は**GMVではなく購入額（円）**。申立ては購入に対して起きるため | 0.5%超、または係争中が1件でもあれば赤。3DS（`STRIPE_3DS`）と「制限値」の新規上限を見直す |

おまけで**決済手段の内訳**も出ます。PayPayはカードより手数料が低いので、比率が上がる
ほど貢献利益率（計画では19.4%）が改善します。

> **「—」は0%ではなく「その期間に取引が無かった」という意味です。** 実効率が0に落ちた
> のかデータが無いのかを区別するため、意図的に0で埋めていません。

> **「(記録なし)」が公開後に増えたら、webhookの記録（0104）が効いていません。**
> `card` に丸めていないのはそのためです。

### 健全性

- **取引データの整合性**（0043）… `check_name` ごとに最新1件。毎日走ります
- **台帳の外部バックアップ**（0047）… 36時間以上動いていなければ赤くなります
- **プッシュ通知**（0064）… 滞留が50件を超えると、pg_cron の確認を促します

### 操作記録

誰がいつ何をしたか。**後から書き換えられません**（読み取り専用のポリシーだけを
置いています）。金銭トラブル・税務・弁護士対応で「誰の判断か」を示すのに使います。

## 最初の管理者を登録する

`admins` テーブルへの書き込みポリシーは意図的に作っていません
（誰でも自分を管理者にできてしまうため）。最初の1人だけ SQL Editor で入れます。

```sql
insert into public.admins (user_id)
select id from auth.users where email = 'あなたのメールアドレス';
```

## まだ画面が無いもの

| 作業 | いまの手段 |
|---|---|
| 退会（匿名化）の実行 | `select public.anonymize_user('<user_id>');`（`docs/data-integrity.md`） |
| 保留を**かける**（`hold_booking`） | 利用者からの申し出・通報で自動的にかかるので、手動で足す場面は稀 |
| コイン失効・自動確定などの定期ジョブ | pg_cron（`docs/web-push-setup.md` / 0015） |
| アイコン・ボイスの強制削除 | `admin_clear_avatar` / `admin_clear_voice_greeting`（本人確認の審査画面から） |
