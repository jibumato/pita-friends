# サービス終了の手順書（規約 第13条2〜5項）

> **これは「使わないことを願う文書」です。** ただし、書いていない手順は実行できません。
> 第13条2〜5項は 2026-07-31 に**当社が自ら約束した内容**なので、
> 履行できる状態にしておかないと、そのまま債務不履行になります。

## なぜ規約に書いたのか

弁護士（総評3・論点8(d)）の指摘：

> **適用除外により資金決済法20条の払戻義務がないからこそ**、規約で自主的に手当てして
> おかないと、消費者契約法10条・不当利得の争点として残る。対価を受けて役務を提供しない
> まま終了する場面の不返金は、議論を免れない。

コインの有効期限を6か月未満にして適用除外を採ったのは事業判断です。その裏返しとして、
**終了時に「払い戻さない」と言い切れない**——というのがこの条項の位置づけです。

## 約束していること（第13条）

| 項 | 約束 |
|---|---|
| 2項 | 終了の**90日前まで**に告知する |
| 3項 | 終了時点で**有効期限内のコインは、残高に相当する額を金銭で返金**する（期限切れは対象外）。**告知時点で期限内なら、その後に期限が来ても返す。無償で付与したコインは対象外**（ただし対価に代えて付与したものは対象） |
| 4項 | 報酬コインは、**最低申請額5,000コインと換金手数料300コインの定めにかかわらず**換金する |
| 5項 | 3項・4項の**方法と期限を、2項の告知で明らかにする** |
| 6項 | 申出の期間は**60日を下回らない** |
| 8項 | 期間経過後は**原則として受け付けない**（例外4号あり。**弁護士確認待ち**） |

## 手順

### T-100日: 判断と準備（告知の前）

1. **終了日を決める。** 告知から終了まで90日以上を確保する（2項）
2. 返金・換金の原資を確認する

```sql
-- 返金・換金にいくら要るか（1コイン=1円）
select
  (select coalesce(sum(remaining), 0) from public.coin_lots
    where kind = 'paid' and remaining > 0 and expires_at > now())    as "返金が要る有償コイン",
  (select coalesce(sum(earned_balance), 0) from public.coin_wallets) as "換金が要る報酬コイン",
  (select coalesce(sum(amount_yen), 0) from public.cash_refunds
    where status = 'pending')                                        as "未払いの返金(円)";
```

> ⚠️ **分別管理口座の残高がこれを下回っていたら、終了の判断より先に資金の手当てが要ります。**
> 分別管理規程の目的そのものなので、ここで足りない状態は規程違反です。

3. **新規の購入を止める。** 告知の前に止めると混乱するので、告知と同時にする

```sql
update public.coin_packs set active = false;
```

### T-90日: 告知（第13条2項・5項）

告知に**必ず含める**もの（5項が「方法および期限を明らかにする」と約束している）：

- 終了日
- **有効期限内のコインの返金**: 方法（振込先の登録）と、申請の期限
- **報酬コインの換金**: 最低申請額と手数料を適用しないこと、申請の期限
- 問い合わせ窓口
- **公式の窓口はここだけである、という注意書き**（下記）
- **個人情報の取扱い**（下記）

告知の場所：アプリ内のお知らせ（`notifications` の全員配信）、トップページ、登録メール。
**アプリ内だけにしない。** 終了間際はログインしない利用者が増えます。

#### 詐欺への注意喚起（必須）

終了告知は**フィッシングの格好の材料**です。「返金手続きのご案内」を騙るメールやDMが
必ず出ます。しかも被害に遭うのはうちの利用者で、**うちが実際に口座情報を集めている
最中**なので、先に言っておかないと「見分けがつかない状態を作ったのは運営だ」という
話になります。告知に次の趣旨を入れます（同業の PLAYONE も同じ注意喚起を出しています）。

> 手続のご案内は、アプリ内のお知らせと、当社の登録アドレスからのメールに限られます。
> **SNSのダイレクトメッセージ、電話、その他の非公式な連絡手段を通じて、
> 個人情報・受取口座情報・アカウント情報をお伝えにならないでください。**
> 当社から、パスワードやクレジットカード番号をおたずねすることはありません。

**送信元アドレスを告知本文に明記する。** 「このアドレス以外は当社ではありません」と
言えるようにしておくのが、一番効きます。

#### 個人情報の取扱い（必須）

終了処理では、平常時より広い範囲の情報を扱います（受取口座、本人確認資料）。
告知に次を書きます。プライバシーポリシーへのリンクだけで済ませない——
**告知しか読まない人が多い場面**なので、そこに書いてあることに意味があります。

- 終了処理のために利用する情報：氏名・連絡先／アカウント情報／取引と役務提供の記録／
  受取口座情報／本人確認資料／問い合わせのやり取りの記録
- 利用目的：返金・換金の実行、本人確認、紛争対応、会計および税務
- **保存期間が満了した後は、削除または匿名化する**こと（電子帳簿保存法7年・
  プライバシーポリシーの保存期間に従う）

#### 告知と規約の関係は、一方向だけ書く

食い違ったときにどちらが優先するかを書いておきます。ただし
**「告知が優先する」とは書かない。**

> 本告知の内容が本規約の定めよりもユーザーに有利である場合には、本告知によります。
> それ以外の点については、本規約および適用法令によります。

**告知一枚で規約より不利な条件に落とせる**書き方にすると、第15条（規約の変更）の
手続を迂回できることになり、その一点で告知全体の信頼性が落ちます。
有利な方向への上乗せに限れば、争点になりません。

#### 告知を更新したときの通知方法を、告知自身に書く

告知は必ず更新されます（期限の延長、窓口の追加、手順の訂正）。
**どこで知らせるかを最初の告知に書いておく**と、後から静かに書き換えたと
言われずに済みます。

> 本告知に更新がある場合は、アプリ内のお知らせ、トップページおよび登録メールにより
> 別途お知らせします。

#### 公開前のチェック

- **同じ内容を2回書いていないか。** 同業の実例で、同趣旨の項が番号違いで
  二重に置かれているものがありました。**どちらが正かは、後で必ず争われます**
- 返金・換金の**期限の日付が、本文中のすべての箇所で一致しているか**
- **第13条の各項と突き合わせる**（2項=90日／3項=有効期限内の**購入**コイン／
  4項=最低額と手数料の不適用／6項=申出期間60日以上／8項=期間経過後の扱い）

### T-90日〜終了日: 受付

- 予約の新規作成を止める（終了日をまたぐ予約を作らせない）
- **すでに成立した予約は履行またはキャンセルまで見届ける**（退会の第6条の2第2項と同じ考え方）
- 換金の申請を受け付ける。**5,000コイン未満でも、手数料300コインも取らない**（4項）

> 換金の最低額と手数料は `request_bank_payout` が判定しています。終了時は
> **この2つを外した migration を当てる**か、運営が `payouts` に直接起票します。
> どちらにするかは、そのときの残件数で決めてください（数十件なら後者が速い）。

### 終了日以降: 返金の実行（第13条3項）

1. 有効期限内のコインを確定させる

```sql
-- 返金の対象（有償のみ。無償で付与したコインは第13条3項ただし書で対象外）
-- ⚠️ 「対価に代えて付与したコイン」（当社の不手際の手当てなど）を bonus ロットで
--    出していた場合は、ただし書の後段により**対象に含める**。該当があるかは
--    coin_transactions の note で確認すること。
select l.user_id, p.nickname, sum(l.remaining)::int as coins, sum(l.remaining)::int as yen
from public.coin_lots l
left join public.profiles p on p.id = l.user_id
where l.kind = 'paid' and l.remaining > 0 and l.expires_at > now()
group by l.user_id, p.nickname
order by yen desc;
```

2. 振込先を集める（本人確認済みの口座があればそれを使う。無ければ請求フォーム）

   > ⚠️ **終了を理由に、新たな本人確認をさせない。** 平常時の換金では本人確認を求めて
   > いますが、終了時に**未確認の人へ改めて確認を課すと、返せない口実**になります。
   > 犯収法上の確認が要る場面（高額・不審）を除き、**登録済みの情報で振り込む**のが原則。
   > できない人が出たら、その人だけ個別に確認する。

3. **振込手数料が残高を上回る／それに近い場合は、本人に確認してから進める**

   ```sql
   -- 振込手数料(仮に165円)を引くと手取りがごく僅か、または赤字になる人
   select l.user_id, p.nickname, sum(l.remaining)::int as yen
   from public.coin_lots l
   left join public.profiles p on p.id = l.user_id
   where l.kind = 'paid' and l.remaining > 0 and l.expires_at > now()
   group by l.user_id, p.nickname
   having sum(l.remaining) <= 500
   order by yen;
   ```

   残高300円の人に165円の手数料を引いて135円振り込むのが本人の希望とは限りません。
   **勝手に手数料を引いて振り込むのも、勝手に「少額だから対象外」にするのも避ける。**
   前者は第13条3項の「残高に相当する額」に反し、後者は約束の不履行です。
   本人に「振込／PayPay等／辞退」を選んでもらい、**選んだ結果を記録に残す**。
   （同業の PLAYONE も「手数料が出金可能な収益額を上回る、またはそれに近い金額と
   なる可能性がある場合、申請者に確認を行ったうえで手続きを進めます」としています。）

4. 振り込む
5. **`cash_refunds` に記録して支払済みにする。** 既存の返金台帳（0085）をそのまま使えば、
   会計仕訳（J19・J20）にも自動で乗ります

### 会計・記録

- **`ledger_export` の外部バックアップを、終了後も保存する。** 法定の保存期間
  （電子帳簿保存法・7年）は終了で消えません
- `accounting_journal()` と `accounting_journal_check()` を最終期でも実行し、
  前受金・預り金が**0に落ちる**ことを確認する
- 終了の記録（告知日・終了日・返金と換金の件数と総額）を1つの文書に残す

## 同業の実例：PLAYONE（2026年5月告知・2026年8月31日終了）

ゲーム向けマッチングの PLAYONE が日本サービスを終了したときの告知を読み比べたものです。
**「業界の実務がどこにあるか」を知っておくと、うちの条項が厚すぎるのか薄すぎるのかが
判断できます。** 結論から言うと、**清算の約束はうちのほうが明確に厚く、
運用の書き方は向こうのほうが具体的**でした。

### スケジュール

| | PLAYONE | ピタフレ |
|---|---|---|
| 告知から終了まで | 約98日 | **90日以上**（第13条2項） |
| 申出の期間 | 終了日まで | **60日を下回らない**（第13条6項） |
| サポート受付の終了 | **終了日と同日** | ——（下記参照） |

告知期間はほぼ同水準です。**サポート受付の終了日を最終日と同じにしているのは
真似しない。** 返金・換金の問い合わせは最後の数日に集中するので、
**サポート窓口は終了日より後まで開けておく**（最低30日）。

### 最大の相違：未使用コインを返すかどうか

PLAYONE は明確に**返していません**。

> 以下の項目は、収益出金の対象には含まれません。
> 1. ユーザーアカウント内に残っている未使用のブルーダイヤ。

残高そのものの扱いは「利用規約、プラットフォーム規則および適用法令に従って
対応いたします」とだけ書き、**明言を避けています**。

対してピタフレ第13条3項は「**残高に相当する額を金銭により返金します**」と
既に約束済みです。これは弁護士の

> 適用除外により資金決済法20条の払戻義務がないからこそ、規約で自主的に手当てして
> おかないと、消費者契約法10条・不当利得の争点として残る

という指摘の、まさに実例にあたります。**うちの水準は業界より上**で、
下げる理由はありません（下げれば9条・10条の争点をこちらから作ることになる）。

### 参考にすべき書き方

1. **申出期間が過ぎた分の扱いを、例外つきで書いている**

   > 期限を過ぎた申請は、**原則として受け付けません**。ただし、期限内に申請され
   > 受理済みの案件、または法令、紛争対応、システム異常、誤りの訂正等による場合は
   > この限りではありません。

   「一切受け付けない」と書くと消費者契約法10条で落ちますが、
   **「原則＋例外の列挙」なら、運用の裁量を残したまま線を引ける。**
   → 規約 第13条に同趣旨を追加済み（8項）。

2. **手数料が残高を上回る場合は本人に確認する** → 上記「返金の実行」3.に反映済み。

3. **対象外を列挙している**（紛争中・違反による凍結中・記録で確認できないもの）
   → うちは第6条の3第3項・第4項が同じ役割を果たしています。

4. **フィッシングへの注意喚起**（§9）→ 上記「告知」に反映済み。

5. **告知そのものに個人情報の節を置いている**（§8）→ 上記「告知」に反映済み。

6. **無償で取得した残高を、返金・出金の対象から外している**

   > 無料配布、キャンペーンによる付与、ミッション報酬、補償、その他無料の方法により
   > 取得されたブルーダイヤは、現金による返金または収益出金の対象には含まれません。

   **これを読んで、うちに実際のずれがあることが分かりました。** 第13条3項は
   「コイン」としか書いておらず、実装（`coin_lots.kind` の `paid`/`bonus`）と
   この手順書は購入分に限っていたのに、**条文だけが広い**状態でした。
   → 第13条3項にただし書を追加（**弁護士確認事項**。`lawyer-questions-2026-08-04.md`
   論点F の後段）。ただし「補償」は一律に外さず、**対価に代えて付与したものは
   対象に含める**留保を置いています。

7. **告知の更新方法を、告知自身に書いている**（§10-11）→ 上記「告知」に反映済み。

8. **告知と規約・適用法令の優先関係を書いている**（§10-10）→ 上記「告知」に反映済み。
   ただし**一方向（有利な場合のみ告知による）に限る**点でうちは書き方を変えます。

### 真似してはいけない点

- **終了時に改めて本人確認を求めている**（「申請者の本人確認、受取口座情報および
  プラットフォームアカウント情報の確認が完了できること」を出金の条件にしている）。
  確認が終わらなければ払わない、という設計は、**返さない口実に見えます。**
- **サポート終了日＝サービス終了日**（上記）。
- **同じ内容を2回書いている**（§10-7 と §10-9 が、ほぼ同文で申請期限後の扱いを
  重複して定めている）。文言が微妙に違うので、**どちらが正かは後で争われます**。
  → 公開前チェックに入れました。
