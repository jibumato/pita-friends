# チャージバックへの防御 — 「120日 対 7日」の現在地

作成日: 2026-08-04

この事業でいちばん深い穴は、**お金が入る時刻と、ひっくり返る期限のずれ**です。
指摘を受けてから対策を重ねたので、**当時の「7日」はもう現状を表していません。**
現時点で何が塞がっていて何が残っているかを、ここ1か所に集めます。

> 各所に残っている税理士・弁護士の引用は**当時の記録なので書き換えません。**
> 数字が古く見えたら、このファイルが現在地です。

---

## 1. 何が120日で、何が7日だったのか

**120日** … 国際ブランドの**チャージバック(異議申立て)の期限**。利用者は取引日から
おおむね120日以内なら「身に覚えがない」「商品が届かない」と申し立てできる。
認められると代金は利用者に戻り、**負担は加盟店(当社)**。

**7日** … 当時の防御。ギフト受領から7日間は換金できない(`0020`・`0069`、
規約 第7条の2第5号)。加えて週次振込(日曜締め・翌週金曜払い)なので、
現金が出るまで最大12日程度。

**桁が一つ違う。** これが指摘の中身でした。

## 2. なぜ致命傷になるのか

コインの経済では、お金が2回動きます。

```
① 利用者がカードでコインを買う        → お金が入る（この後120日ひっくり返りうる）
② ピタメイトが換金して銀行振込を受ける → お金が出る（数日〜十数日で完了）
```

**すでに他人に渡したお金を、あとから請求される**という時間差が生まれます。

防御が7日しかなかった場合の最悪ケース:

| 経過 | 出来事 |
|---|---|
| 0日目 | 盗んだカードで50,000円分のコインを購入 |
| 1日目 | そのコインで別アカウント(本人)に予約・ギフト |
| 8日目 | 保留明け。換金申請 |
| 12日目 | **銀行振込を実行。現金が外へ出る** |
| 90日目 | カードの本来の持ち主が明細に気づいて申立て |
| 100日目 | チャージバック成立。**50,000円が当社から引かれる** |

12日目の時点で手元に原資はありません。**88日後に、返す原資が無い状態で請求が来ます。**

## 3. 規約では埋まらない

> 規約でピタメイトに返還義務を課すことは可能ですが、**善意の受領者から既払金を
> 回収するのは実務上ほぼ不可能で、規約は防御になりません。**
> **設計で防ぐべきで、最も効果が大きいのは EMV 3-Dセキュア(3DS2)の適用**です。
> —— 税理士 第2回回答(2026-07-30)

不正をしたのは購入者で、報酬を受け取ったピタメイトは通常なんの落ち度もありません。
その人から取り立てることは実際にはできず、訴えても費用倒れです。

弁護士も同じ方向で、**支払済み金銭の返還請求条項は置くな**と限定しています
(規約 第8条の6第4項2号)。置けば片面的なリスク転嫁条項として
消費者契約法10条で無効になるリスクのほうが大きい。

## 4. 現在の防御 — 実装済みのもの

| 防御 | 内容 | 実装 |
|---|---|---|
| **3Dセキュア2の強制** | `request_three_d_secure: 'any'`。認証が成立した取引は**不正利用型チャージバックの責任がカード発行会社へ移転**(ライアビリティシフト)。**最大の柱** | `create-checkout-session/index.ts` |
| **新規ユーザーの購入上限** | 登録`new_user_days`(既定30)日以内は、1回¥10,000／期間¥30,000まで。**被害額そのものに天井をかける** | `0087` |
| **新規ユーザー原資の換金保留** | 新規ユーザーの購入を原資に含む換金申請は**最長30日保留**(`payouts.hold_until`)。7日→30日。条文が「最長30日」と画しているので、31日以上は入れられない制約付き | `0088` |
| **係争中の報酬の凍結** | `charge.dispute.created` を受けたら、その購入**以後**の予約に紐づく報酬を決着まで換金保留 | `0077` |
| **ギフトの7日保留** | 受領から7日は換金不可 | `0020`・`0069` |
| **相殺** | 購入が失効したとき、**未払の**報酬コインから、**その購入から現に充当された分だけ**控除。通知 → 異議の機会(7日) → 運営が実行の3段で、cronでは走らせない | `0088`・規約 第8条の6 |
| **カードのフィンガープリント監視** | 自作自演(自分のカードで買ったコインを別アカウントの自分へ送って換金)の検知。**PayPay払いには効かない**ので、判定できない購入の件数を換金画面に出す | `0080`・`0096` |

数値は `platform_pricing` にあり、**運営コンソールから変えられます**
(コードの再デプロイは不要)。

## 5. 残っているギャップ

**登録から30日を過ぎた利用者の購入を原資とする報酬。**
予約なら検収後すぐ、ギフトなら7日で換金可能になるので、
ここには120日の期限が丸ごと残ります。

全員の換金を30日止めれば塞げますが、**まともなピタメイトが逃げます。**
弁護士も「無限定の『当社はいつでも換金を保留できる』は10条リスクそのもの」と
釘を刺しています。

> チャージバックは取引後数十日に集中する傾向があるため、③(リスクベースの換金保留)を
> 新規・高リスク層に絞って置くだけで、**120日と7日のギャップの実害は相当圧縮できます。
> 残余は事業リスクとして引き当てるほかありません。**
> —— 弁護士 回答(2026-07-31)

**「相当圧縮」であって「解消」ではない。** ここは引当てで受け止める前提です。

> ⚠️ **あんしんサポート料をこの損失填補の原資と説明しないこと。**
> 自ら保険構成を招きます(弁護士が明示的に禁止)。

## 6. PayPayが効く理由

ウォレット決済には、カードのような異議申立ての窓が**存在しないのが一般的**です。
そうであれば、PayPayで買われた分にはこの穴がそもそも開きません。
決済手数料も通例カードより低いので、珍しく両取りできる話です。

> **ただし断定はできません。** Stripeの決済手段一覧でPayPayの
> **「Disputes(異議申立て)」の欄**を確認してください。「あり」ならこの期待は
> 成り立ちません。手順は `payments-stripe-setup.md` §5-c。

カードからPayPayへ需要が移った比率だけ、この構造的リスクは減ります。
一方で**自作自演の検知は弱くなります**(§4の最終行)。両方を見て判断してください。

## 7. 会計 — 金額より怖いのは決済手段を失うこと

> 「支払手数料(決済代行)」とは**別に「支払手数料(チャージバック)」の補助科目**を。
> 理由は会計上の必要ではなく**これが事業の健全性を示す指標だから**。
> チャージバック率が上がるとStripe側から加盟店契約の見直し・保証金の要求・
> 契約解除を受けることがある。**決済手段を失うと事業が止まります。**
> —— 税理士 第2回回答

開業時の会計設定で、この補助科目を必ず作ってください
(`docs/accounting-monthly-close.md`)。
