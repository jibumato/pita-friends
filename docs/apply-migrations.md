# マイグレーションの適用手順（あなたの手元で実行）

このリポジトリを開発しているサンドボックス環境は、ネットワークポリシーによりあなたのSupabaseプロジェクトへ接続できません。そのため、**マイグレーションの適用はあなたの手元で行ってください。** 以下のいずれかの方法で数分で完了します。

---

## 方法A: SQL Editorに貼り付け（CLI不要）

> ⚠️ **運用中の本番に `supabase/schema-all.sql` を貼らないでください。**
> 全マイグレーションを連結したもので、**空のデータベースを最初に作るときだけ**の
> ためのものです(既にあるテーブル・関数とぶつかります)。いまは大きすぎて
> SQL Editor が受け付けませんが(2026-10-17 に実際に拒否された)、CLI 等で
> 流せば壊れます。この節は以前「schema-all.sql を全部貼る」と書いていました。

**本番に追加分を当てる手順:**

1. `docs/check-migrations.sql` を SQL Editor で流し、「次に適用するファイル」を見る
2. その番号から始まる**パート**を `supabase/apply/` から選ぶ
   (いまは `supabase/apply/0096-0128/` に part1〜part4)
3. パートの中身を全部貼って **Run**。終わったら 1. をもう一度流し、
   「次に適用するファイル」が進んだことを確かめてから次のパートへ
4. 最後のパートのあとに「すべて適用済み」になれば完了。続けて
   `docs/check-cron.sql` で定期ジョブを確かめる

各パートは1つのトランザクションとして流れるので、**途中でエラーになったら
そのパートは何も当たりません**。そこで止めて、エラーの内容を確かめてください。
パートの先頭には関所があり、**順番を飛ばしたときと、同じパートを二度流した
ときは、何もせずにエラーで止まります**(順番を飛ばしても多くのマイグレーションは
エラーにならずに通ってしまうため)。

パートは `python3 tools/bundle-migrations.py <開始番号> <終了番号>` で作ります
(1パート約120KB)。**当て終わったら、そのフォルダは消してかまいません。**

## 方法B: Supabase CLI（`supabase db push`）

CLIをすでにお使いなら、こちらの方が今後のマイグレーション管理が楽です。

```bash
npm install -g supabase        # 未インストールなら
supabase login                 # ブラウザでトークン認証
supabase link --project-ref ytxsyklnqepanloomzcw
supabase db push               # supabase/migrations/ を番号順に適用
```

> ⚠️ **これまで SQL Editor で当ててきた本番では、そのまま `db push` しないこと。**
> CLI は自分で当てた記録(`supabase_migrations.schema_migrations`)しか見ないので、
> **`0001` から全部当て直そうとして壊れます**。CLI に切り替えるなら、先に
> 当て済みの番号を `supabase migration repair --status applied <番号>` で
> 記録させてから使ってください。迷ったら方法Aのパートを使うほうが安全です。

## 適用後にやること

### 1. アプリを起動して接続確認

`.env.local` はこのリポジトリに用意済みですが、`.gitignore` 対象なので**あなたの手元には無い場合があります**。無ければ以下を作成してください（値はSupabaseの `Settings > API Keys`）。

```
VITE_SUPABASE_URL=https://ytxsyklnqepanloomzcw.supabase.co
VITE_SUPABASE_ANON_KEY=（Publishable key。sb_publishable_ で始まる）
```

> レガシーの `anon public` キー(`eyJ...`)は使いません。Edge Functions が
> `UNAUTHORIZED_LEGACY_JWT` で拒否します。

```bash
npm install
npm run dev
```

ブラウザのコンソールに `デモモードで起動します` が**出なければ**接続成功です。「PRESS START」からメール＋パスワードでアカウントを作成できます。

> Supabaseの `Authentication > Providers > Email` で「Confirm email」が有効な場合、サインアップ後に確認メールのリンクを踏む必要があります。テストを簡単にしたい場合は一時的にオフにできます。

### 2. 自分を管理者に登録（本人確認の審査に必要・初回のみ）

先にそのアカウントで一度サインアップ／ログインしてから、SQL Editorで:

```sql
insert into public.admins (user_id)
select id from auth.users where email = '<あなたのログインメールアドレス>';
```

以降、そのアカウントの **設定画面 → 管理者メニュー → 本人確認の審査** から、提出された本人確認を承認/却下できます。

### 3. 動作確認の流れ

1. アカウントA（あなた／管理者）でログイン
2. アカウントB（テスト用・別メール）でサインアップ → 本人確認で書類・顔写真を提出（テストなので手元の画像でOK）
3. アカウントAの管理画面で承認
4. アカウントBで「ホストになる」→ 掲載 → アカウントAの「さがす」にアカウントBが表示される → 予約

これで、認証・プロフィール・本人確認・ホスト掲載・さがす・予約（コイン消費）まで実データで一気通貫に動くことを確認できます。

## 私（サンドボックス側）でできること・できないこと

- ✅ できる: コードの修正、マイグレーションSQLの追加・修正、型チェック、ビルド、デモモード（バックエンド未接続）での画面確認
- ❌ できない: あなたのSupabaseへの接続を伴う操作（マイグレーション適用、実データでの動作確認）— ネットワークポリシーで遮断されているため

適用中にエラーが出た場合は、そのエラーメッセージを教えていただければ、SQLを修正します。

## どこまで適用したか分からなくなったら

`docs/check-migrations.sql` を SQL Editor に貼って実行してください。
**読み取りだけ**で、データもスキーマも変更しません。

出るもの:

- マイグレーションごとの ✅ 適用済み / ⬜ 未適用
- **次に適用するファイル**
- **順番の飛び**があればその警告

適用履歴を持つ表が無い(SQL Editorから手で流す運用)ため、
「そのマイグレーションでしか作られないもの」が実在するかで判定しています。
目印には、列やテーブルのように**追加されたら消えない**ものを優先しています
(関数の中身は後のマイグレーションで差し替わるため、目印に向きません)。

### 順番の飛びが出たら

`0038` `0040` `0041` `0048` `0049` `0051` は**いずれも `create_booking` を
差し替えます**。飛ばした番号があると、後から当てた古いほうが新しい修正を
打ち消している可能性があります。**飛ばした番号から順に当て直してください**
(0037〜0051 は**何度流しても壊れない**ように書いてあります。
すでに当てたものが混ざっていても、番号順に全部流し直して構いません。
まっさらな状態から通し、その上に2回重ねて流して確認しています)。
