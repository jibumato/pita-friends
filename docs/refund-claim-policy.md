# 個別相談（返還の申し出）の判断基準

利用規約 **第9条2項**の窓口——「提供された内容が合意した内容と著しく異なる場合」
の相談——をどう捌くかの運用基準です。

キャンセル（第9条1項）は時刻から機械的に決まるので判断が要りません。
**人手の判断が残るのはここだけ**なので、先に基準を決めておきます。基準が無いまま
始めると、対応が担当者の気分で揺れ、後から「あの人には返したのに」と言われます。

---

## 0. 前提: 何を守るための窓口か

規約に一律のルールを置いても、消費者契約法10条（消費者の利益を一方的に害する条項）
の観点では**個別救済の余地を残しておくほうが安全**です。この窓口はそのための
安全弁であって、「交渉すれば返ってくる窓口」ではありません。

同時に、ここを緩くすると「使ってから申し出する」が成立し、キャンセル規定が
骨抜きになります。**線引きを先に決めておくことが、緩さと厳しさの両方を防ぎます。**

---

## 1. 最初の分岐: 役務が提供されたか / 品質に不満か

**この一線がすべての起点です。**

| | 扱い |
|---|---|
| **役務が提供されなかった** (来ない・すぐ消えた・大幅遅刻で実質遊べていない) | 返還の検討対象 |
| **提供されたが期待と違った** (実力が思ったより低い・話が合わない・雰囲気が悪い) | **原則として返還しない**。評価・レビュー制度で処理する |

品質への不満まで返還対象にすると、判断が無限に必要になるうえ、
「遊んでから返金を求める」が成立してしまいます。**主観的な満足度は返還ではなく
評価で解決する**、という切り分けを崩さないでください。

ただし「実力が違う」が**虚偽の申し出**（プロフィールに書いたランクが事実と違う）に
まで至る場合は、品質の問題ではなく**規約違反**なので、返還ではなく
第6条（利用制限）の対象として処理します。

---

## 2. ケース別の判断表

判断は「返す／返さない」の二択にしません。**提供された分は差し引く**ことで、
中途半端なケースを合理的に処理できます。

| 状況 | 返還 | 原資 | 備考 |
|---|---|---|---|
| ピタメイトが現れなかった | 全額 | ピタメイト | ドタキャン記録に反映 |
| 開始後まもなく離脱して戻らない | 全額 | ピタメイト | 「まもなく」は予約時間の1/4を目安 |
| 途中で離脱（相当時間は遊んだ） | 遊べなかった時間分 | ピタメイト | 30分単位に丸める |
| 大幅遅刻で実質遊べていない | 全額 | ピタメイト | 予約時間の1/2以上が失われた場合 |
| 遅刻したが残りは遊べた | 遅刻分 | ピタメイト | |
| 暴言・ハラスメント等の規約違反があった | 全額 | ピタメイト | **返還と別に**第6条の措置を必ず行う |
| プロフィールの記載が虚偽だった | 全額 | ピタメイト | 同上 |
| ゲーム側のサーバー障害で遊べなかった | 全額 | **当社** | どちらにも帰責しない。ここは費用として飲む |
| ピタフレ側の障害 | 全額 | **当社** | 第9条3項の範囲 |
| ゲスト側の回線・機材の問題 | なし | — | ピタメイトは待機している |
| 期待と違った・合わなかった | なし | — | 評価で処理 |

**「原資」を必ず決めてください。** ここを曖昧にすると、返還のたびに
「誰の負担か」で揉めます。

---

## 3. 少額は事実確認をしない（閾値運用）

事実確認そのものにコストがかかります。**確認コストが返還額を上回る領域では、
確認せずに返すほうが合理的です。**

- **1,000コイン以下**かつ**過去180日で1回目**の申し出 → 事実確認せず返還（原資は当社）
- それを超える場合 → 下記の確認を行う

これは甘さではなくコスト最適化です。ただし**回数を必ず記録**してください。
記録しないと閾値運用が「言えば毎回返る」に変質します。

---

## 4. 事実確認で見るもの（記録から分かること優先）

「言った・言わない」に踏み込むほどコストが上がります。**先にシステムの記録を
見て、それで決まるなら決める**という順序を守ってください。

見る順に:

1. **トークのタイムスタンプ** — 合流のやりとりがあるか。予約時刻の前後に会話が
   途切れていないか。無言のまま終わっていれば「来なかった」の裏づけになる
2. **プレイ完了の確定操作** — ゲストが自分で確定していれば、原則として納得の表明。
   ただし**72時間の自動確定は納得の表明ではない**（何もしなかっただけ）。
   ここを混同しないこと
3. **通報の有無** — その場で通報していれば申し出の信憑性は高い。後出しは低い
4. **双方の過去の記録** — ドタキャン率・マナースコア・過去の申し出回数
5. （ここまでで決まらない場合のみ）**双方への聴取**

---

## 5. 濫用の検知

| 兆候 | 対応 |
|---|---|
| 同一ゲストの申し出が180日で3回以上 | 閾値運用の対象外にし、以後は必ず事実確認 |
| 申し出のたびに相手が異なる | ゲスト側の問題を疑う。利用制限の検討 |
| 同一ピタメイトへの申し出が複数のゲストから | **掲載停止を検討**。個別返還ではなく供給側の是正 |
| コイン購入直後に高額の申し出 | 現金化の疑い。換金・ギフトの制限とあわせて確認 |

最後の行は第7条の2第6項（ギフトの濫用防止）と同じ観点です。

---

## 6. 申し出の期限

**期限は「自動確定より内側」でなければ機能しません。** ここが設計の要です。

プレイ完了は**予約の終了時刻から72時間で自動確定**し、確定した瞬間に
対価はピタメイトの換金可能残高に入ります。**確定後に申し出が来ても、原資を
ピタメイトから回収する手段がありません。** したがって:

> **受付の開始に制限はありません。** 下の表はすべて**締め切り**の話です。
> 予約が成立した瞬間から申し出られますし、通報にも時間の条件はありません
> (`0042` の保留も通報した時点で効きます)。
> 「相手が来ない」と気づいたゲストが**終了時刻まで待つ必要はない**、という点は
> `0050` の自動処理でさらに明確にしています(後述)。

| | 締め切り | 理由 |
|---|---|---|
| **原則**(ピタメイトから回収するもの) | プレイ**終了**から**48時間** | 自動確定(**終了**+72時間)より24時間内側 |
| **少額枠**(§3・当社が飲むもの) | プレイ**終了**から**7日** | 回収が要らないので自動確定と競合しない |

締め切りを**終了**基準にしているのは、開始基準にすると長い予約ほど
「終わった後の猶予」が短くなり、かえって不利になるためです
(8時間の予約なら、開始+48時間は終了後40時間しか残らない)。

> **`0048` で自動確定の起点を開始時刻から終了時刻に変えました。** それ以前は
> 開始+72時間だったため、プレイ時間の上限を延ばすと猶予が縮み、延長を重ねると
> **プレイ中に確定してしまう**状態でした(延長には総時間の上限が無かった)。
> 起点を揃えたことで、プレイ時間の上限を何時間にしても猶予は常に24時間残ります。

少額枠だけ長くできるのは、**回収の必要がない申し出には自動確定が制約にならない**
ためです。期限を一律に短くする必要はありません。

### 期限を過ぎたら

返還の対象にはしませんが、**規約違反の通報としては期限なく受け付けます**。
なりすまし・詐欺的行為・ハラスメント等は、返還とは別に第6条の措置を行います。
「期限切れだから何もしない」ではありません。

### 48時間で足りるか

「相手が来なかった」ほど明確なトラブルは、その場か翌日には申し出が来ます。
一方、深夜に終わった予約→翌日は仕事、で丸1日空くことはあるため、24時間では
短すぎます。48時間はその間を取った数字です。

ただし**期限が短いこと自体が消費者契約法10条(消費者の利益を一方的に害する条項)
の論点になりえます**。48時間の合理性は「役務提供型で、記録が揮発しやすく、
相手方への支払が発生する」という性質から説明する想定です。弁護士査読の対象に
含めてください。

## 6-b. 他サービスとの比較（メルカリ）

フリマ(メルカリ)は**発送通知から9日程度**で自動的に取引完了とし、売上を確定
させると聞いています〔※事業者から共有された情報。**一次資料で未確認**であり、
規約は改定されるため、判断の根拠にする場合は原文を確認すること〕。

**数字はそのまま使えません。** 9日という長さは**物流のリードタイムがあるから**です。

| | フリマ | ピタフレ |
|---|---|---|
| 起点 | 出品者の**自己申告**(発送通知) | `scheduled_at`(**システムが知っている時刻**) |
| 引渡しまでの不確実性 | 数日かかる。遅延・不在持ち戻りもある | **無い**。予約時刻に始まり数時間で終わる |
| 後からの検証 | 物が手元に残るので可能 | 役務は**その瞬間にしか存在しない**。時間が経つほど証拠が薄れる |
| 供給側の資金繰り | 元々持っていた物が売れた形。待てる | 時間を提供している。9日待ちは体験が悪い |

物流が無く、起点が客観的で、証拠が揮発しやすい以上、**こちらは短く締めるほうが
合理的**です。72時間は短すぎません。

### ただし構造は参考になる（というより裏づけになる）

一般に、この種のエスクローでは**事務局が介入している取引は自動完了しない**扱いに
なっているとされます。これは本文書が下記「実装の穴」で必要としている
**保留フラグそのもの**です。

つまり保留フラグは特殊な作り込みではなく、**エスクローを持つマーケットプレイスの
標準装備**と考えるべきものです。E-12 を「後回しでよい改善」ではなく
**窓口を開ける前提条件**として扱う根拠になります。

なお起点の取り方は、こちらのほうが有利です。フリマは出品者の自己申告(発送通知)を
起点にせざるを得ませんが、ピタフレは予約時刻をシステムが知っているため、
**申告に依存しません**。

---

## 7. 記録として残すもの

判断のたびに次を残してください。**一貫性を保つためと、消費者契約法9条の
「平均的な損害」を主張する際の材料になるため**の両方です。

- 予約ID / 申し出日時 / 申し出内容
- 適用した判断（上記表のどの行か）
- 返還額と**原資**
- 判断の根拠（見た記録）
- 対応者

キャンセル側の材料は `guest_cancellation_evidence` ビュー（0032・0040）に
集まっています。申し出側も同じ粒度で残すと、後から突き合わせられます。

## 保留の仕組み（E-12・`0042` で実装済み）

### 基本の形

**終了時刻+72時間で自動確定。ただし保留フラグが立っている予約は確定しない。**
(`0048` より前は開始時刻が起点でした。)

`0042` で実装済みです(`bookings.held_at` / `hold_reason`、
`auto_complete_bookings` の除外条件、保留・解除のRPC、一覧ビュー)。

期限を48時間に収めても、それだけでは足りません。48時間以内に申し出が来ても、
担当者が着手する前に72時間が経てば確定します(47時間目の申し出に25時間以内で
必ず着手できる保証はない)。期限の短縮は**構造的な問題を対応速度の問題に
変えるだけ**です。

必要なのは「**受け付けた事実だけで自動確定を止める**」ことです。判断まで
待ちません。実装は `bookings` に列1本、自動確定ジョブ(`0015`)の抽出条件に1行。

### 保留の引き金は「申し出」だけにしない

ここが設計の穴です。**申し出をしないゲストがいます。**

ピタメイトが来なかった → がっかりしてアプリを開かなくなる → 申し出もしない
→ 72時間後に自動確定 → **来なかったピタメイトが満額受け取る**。
泣き寝入りが最も起きやすく、しかも**一番悪質なケース(無断欠席)で起きます**。

引き金は次の3つにします。

| 引き金 | 保留 | 備考 |
|---|---|---|
| 返還の申し出 | する | 本来の経路 |
| **その予約に対する通報** | **する** | 申し出より心理的ハードルが低い。既に実装済みの導線を活かす |
| 合流の形跡が無い(予約時刻の前後にメッセージが1件も無い) | **しない** | 自動保留は誤検知でピタメイトを不当に待たせる。下記のとおり事後の監視に回す |

3つ目を自動保留にしないのは、**Discord等で合流してアプリでは喋らない**ケースが
普通にあるためです。ただし放置もしません。**完了済みのうち合流の形跡が無いものを
集計し、特定のピタメイトに偏っていたら掲載停止**を検討します。個別の回収は
諦めますが、繰り返させません(供給側の是正)。

### 保留したままにしない（出口を必ず作る）

保留はピタメイトの資金を凍結します。**黙って凍結すると不信を招きます。**

- 保留した時点で**ピタメイトに通知**する(「申し出があったため確定を保留しています」)
- **保留にも期限を置く**(例: 14日)。過ぎたら担当者に督促が出るようにする。
  判断しないまま放置される状態を作らない
- 解除の経路を2つ用意する
  - 申し出を認める → 一部/全額を返還し、残りを確定
  - 申し出を退ける → そのまま確定

### ゲスト自身が確定した後は保留できない

「プレイ完了・支払いを確定する」を押すと即座に報酬が渡るため、その後の
申し出は回収できません。ボタンの文言は現在
「**✓ プレイ完了・支払いを確定する**」で、支払いが確定することは伝わっています。
この文言を弱めないでください(「完了」だけにすると、支払いが動くと分からない)。

### 採らなかった案

- *確定後に `earned_balance` から差し引く* — 残高が無ければ回収できない
- *自動確定を9日等に延ばす* — ピタメイトへの支払いが遅くなる。物流がある
  フリマと違い、こちらは遅らせる理由が無い(§6-b)
- *当社負担で固定する* — 単純だが濫用に弱い

## 操作手順（運営）

すべて管理者(`admins` に登録されたアカウント)としてのみ実行できます。
現時点では専用画面が無いため、**Supabase の SQL Editor から実行**してください。

### 1. 申し出を受けたら、まず止める

判断より先に止めます。判断を待っていると自動確定に間に合いません。

```sql
select public.hold_booking('<booking_id>', 'claim');
```

`true` が返れば保留できています。`false` は**すでに確定済み**で手遅れ、
または既に保留中です。`bookings.status` を確認してください。

> 通報が引き金の場合は**自動で保留されます**。操作は不要です。

### 2. 保留中の一覧を見る

```sql
select * from public.held_bookings_overview;
```

`is_overdue` が `true` のものは、保留したまま14日を過ぎています。
**ピタメイトの資金を凍結し続けている**状態なので、優先して処理してください。

### 3. 判断して解除する

判断基準は本文書の §1〜§5 に従います。

```sql
-- 申し出を認める(割合を指定。100=全額返還 / 0=返還なし)
select public.release_hold_and_refund('<booking_id>', 50, '合流の形跡が無いため半額返還');

-- 申し出を退けて、そのまま報酬を確定する
select public.release_hold_and_complete('<booking_id>', '双方のやりとりを確認し、役務は提供されていた');
```

第3引数(メモ)は `bookings.cancel_reason` に残ります。§7 の記録の一部として
必ず書いてください。どちらのRPCも、双方に通知が飛びます。

### 4. 事後の監視（供給側の是正）

個別の回収を諦めたケースでも、繰り返させないために偏りを見ます。

```sql
-- 直近90日、保留になった回数が多いピタメイト
select host_id, count(*) from public.bookings
where held_at is not null and scheduled_at > now() - interval '90 days'
group by host_id order by count(*) desc;
```

特定のピタメイトに偏っていれば、**掲載停止**を検討します（§5）。

## 9. 無断欠席は運営が判断しない(`0050`)

相手が来なかったゲストが取れる自己解決の手段は、以前は「キャンセル」だけでした。
それは**ゲスト都合**として処理されるため、相手が来なかったのにゲストが没収される、
という筋の通らない状態になります。正しい行き先は通報ですが、「通報」という言葉は
心理的に重く、面倒がって黙って去る人が出ます。

かといって運営が「本当に来なかったのか」を判定するのは不可能です。Discordに移って
遊ぶことが普通にあるので、チャットの沈黙は不在の証拠になりません。

そこで**運営が観測しようとせず、当事者の不作為で決まる**形にしました。

```
開始時刻を過ぎると、両者に「はじめました」ボタン
  ※ ピタメイトがメッセージを1通でも送れば自動でチェックイン扱い

開始+15分(自動)   ゲストのみチェックイン済み → 予約を保留。お金が止まる。両者に通知
保留中(自動)      ピタメイトがチェックイン    → 保留を解除。通常フローへ
保留+24時間(自動) 一度も反応なし              → no_show_host。全額返還+ドタキャン記録
```

**この流れに運営は一度も登場しません。**

| なぜ悪用されないか | |
|---|---|
| ゲストが嘘をつく | 結果を決めるのはゲストのボタンではなく**ピタメイトの不作為**。相手が一言でも喋れば無効 |
| ピタメイトが押し忘れる | 15分後に通知が飛び、24時間の猶予があり、**メッセージでも救われる** |
| 無料キャンセルの抜け道 | 押して起きるのは**お金を止めること**だけ。返還は24時間の無反応が条件 |

猶予15分・確定24時間は `platform_pricing`(`checkin_grace_minutes` /
`no_show_resolve_hours`)で変えられます。運用しながら調整してください。

```sql
-- 無断欠席で保留中のものを見る(督促や様子見に)
select * from public.held_bookings_overview where hold_reason = 'no_show';
```
