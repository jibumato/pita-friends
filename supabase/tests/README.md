# ローカルPostgresでのマイグレーション検証

Supabase に触れずに、ローカルの PostgreSQL でマイグレーションを通しで適用し、
コインの返金まわりの挙動を確認するための一式です。

`0030_refund_lot_expiry.sql`(返金コインの有効期限)の検証に使いました。
本番DBには一切触れません。

## 使い方

```bash
# 1. ローカルPostgresを起動(初回のみ initdb)
export PGDATA=$HOME/pgdata
/usr/lib/postgresql/16/bin/initdb -D "$PGDATA" -U postgres --auth=trust
/usr/lib/postgresql/16/bin/pg_ctl -D "$PGDATA" -o '-p 55432 -k /tmp' -l /tmp/pg.log start

# 2. まっさらなDBを作り、Supabase相当のシムを入れる
psql -h /tmp -p 55432 -U postgres -c "drop database if exists pita"
psql -h /tmp -p 55432 -U postgres -c "create database pita"
psql -h /tmp -p 55432 -U postgres -d pita -c "create extension if not exists pgcrypto"
psql -h /tmp -p 55432 -U postgres -d pita -c "create publication supabase_realtime"
psql -h /tmp -p 55432 -U postgres -d pita -c "create role anon nologin; create role authenticated nologin; create role service_role nologin" 
psql -h /tmp -p 55432 -U postgres -d pita -f supabase/tests/00_supabase_shim.sql
psql -h /tmp -p 55432 -U postgres -d pita -f supabase/tests/01_storage_shim.sql

# 3. マイグレーションを番号順に全適用
for f in supabase/migrations/*.sql; do
  psql -h /tmp -p 55432 -U postgres -d pita -q -v ON_ERROR_STOP=1 -f "$f" || { echo "FAIL $f"; break; }
done

# 4. テストを流す
psql -h /tmp -p 55432 -U postgres -d pita -f supabase/tests/10_refund_expiry.sql
```

> ロールは DB をまたいで共有されるため、2回目以降 `create role` はエラーになります
> (無視して構いません)。

## シムについて

Supabase 固有のものだけを最小限に置き換えています。

| シム | 中身 |
|---|---|
| `auth.users` | id と email だけのテーブル |
| `auth.uid()` | `current_setting('test.uid')` を返す。テスト中に `set test.uid = '<uuid>'` で切り替える |
| `storage.buckets` / `objects` / `foldername()` | 本人確認画像・アバター用の最小定義 |
| `cron.schedule()` | 何もしないダミー(0018がジョブ登録を呼ぶため) |

`set local` ではなく **`set`** を使ってください。psql の各文が独立トランザクション
になるため、`set local` だと次の文に効きません。

## テストの内容

| ファイル | 確認すること |
|---|---|
| `10_refund_expiry.sql` | 5か月前に購入したコインで予約→辞退したとき、返金分が**当初の期限のまま**戻ること(0030の本体) |
| `11_refund_lapsed.sql` | 返金までに当初の期限が切れていた場合、戻さずキャッシュ残高から差し引き、`expire` の取引履歴が残ること。`restored_at` が入って二重返金されないこと |
| `12_refund_legacy_fallback.sql` | 0030より前に作られた消費記録の無い予約でも、予約作成時刻を基準に期限を引き直すこと |
| `20_monitoring_consent.sql` | みまもり同意の記録(0031)。同じ版で二重記録されないこと、文言改定で新しい行が積まれること、撤回で全行に `revoked_at` が入ること、撤回後に再同意できること、未ログインでは何も起きないこと |

### 0030 の効果を確認する

0030 を**除いて**適用すると `10_refund_expiry.sql` 相当のケースが落ちます
(返金分が「今から6か月後」の新しい期限になり、当初の発行日からの通算で
約11か月使えるコインが生まれる)。0030 を含めると当初の期限を引き継ぎます。

### `30_cancellation_evidence.sql` について

E-1(ポリシー版の記録)とE-2(立証材料ビュー)の確認に加えて、
**キャンセルポリシーの表示が実態と食い違っている問題**(open-issues.md の E-10)を
再現します。承諾直後にゲストがキャンセルしても全額没収されることを、
実際にコイン残高で確認できます。

### `40_host_fees.sql` について

ホスト手数料(0033)の検証です。累進の段(20/17/14/12%)、指名リピート割引
(−3pt・下限10%)、ギフトの一律30%、ティア境界をまたぐ予約の4ケースを、
手計算と突き合わせて確認します。

このテストで **トリガーの発火順序のバグを1件発見しました**。`complete_booking` は
「予約を completed にする」→「報酬を満額付与する」の順で書かれているため、
通常の `AFTER UPDATE` トリガーだと付与より前に手数料を引こうとして、残高が
無いところからの控除が丸ごと消えます(1件目の400コインが消えました)。
`deferrable initially deferred` の制約トリガーにして解決しています。

### `50_host_dashboard.sql` について

ホスト向けダッシュボードの集計(0034)。ゲスト2人(1人はリピート・1人は新規)と
辞退1件の状況を作り、手数料・実効料率・リピート率・成約率・時間帯が正しく
出るかを見ます。`_fixture_host.sql` が共通のデータ投入です。

ここでも1件バグを見つけました。リピーター数と新規数を単純に filter で数えると、
初回と2回目が同じ月にあるゲストが**両方に二重計上**されます(新規1人のはずが2人)。
差し引きで出すよう修正しています。

### `60_extension.sql` について

延長課金(0035)。進行中の予約に+30分して、時間・コイン・支払コインが増えること、
**延長分もロット記録に残ること**(残らないと0030の返金で期限を引き直されてしまう)、
完了時の手数料が延長後の総額にかかること、完了後は延長できないことを確認します。

### `70_cancel_board_post.sql` について

募集の取り消し(0036)。他人は取り消せないこと、作成者は理由つきで取り消せること、
**参加者全員に通知が届くこと**、連打しても通知が増えないこと、直接UPDATEの
ポリシーが外れていることを確認します。

### `95_scheduled_cancel.sql` について

開始時刻の指定と段階制キャンセル(0040)。受付範囲(30分先〜7日先)の検査、
**承諾しても希望開始時刻が上書きされないこと**(E-10の本体)、開始3時間前は全額・
開始40分前は50%・開始後は0%になること、一部返還でも残高とロット合計がずれない
こと、「今すぐ」でも承諾から5分は全額戻ること、返還率を platform_pricing で
変えられることを確認します。

ここでも設計の穴を1つ見つけました。猶予の条件に「開始前であること」を入れて
いたのですが、「今すぐ」の予約は開始時刻＝承諾時刻なので、この条件が猶予そのものを
打ち消してしまい、**まさに直そうとしていた「承諾の瞬間から100%没収」が残る**
状態でした。猶予は開始時刻と切り離しています。

> なお `40_host_fees.sql` と `60_extension.sql` は同じフィクスチャ
> (`_fixture_host.sql`)を使うため、同一DBに続けて流すと2本目が
> 重複キーで落ちます。どちらかを流す前に作り直してください。
> `60_extension.sql` が最後に出す `BOOKING_NOT_EXTENDABLE` は**期待どおりの結果**です
> (完了後は延長できないことを確かめている)。

### `97_booking_hold.sql` について

自動確定の保留(0042 / E-12)。保留していなければ従来どおり72時間で確定すること、
**保留中は確定も報酬の移動も起きないこと**、ピタメイトに保留の通知が届くこと、
管理者以外は保留・解除できないこと、一部返還(50%)が正しく分配されること、
解除後の再解除が `NOT_HELD` で弾かれること、**通報が自動的に保留の引き金に
なること**、保留したまま14日を過ぎたものが督促対象として一覧に出ることを
確認します。

7番目が設計上いちばん重要です。相手が来なかったゲストは申し出をせずに
黙って去ることが多く、それを放置すると**無断欠席した側が満額受け取ります**。
通報を引き金にすることで、心理的ハードルの低い導線から救えます。

### `96_longer_bookings.sql` について

30分刻み・最長4時間の予約(0041)。旧3択に無かった90分が正しい料金(時給1000で
1500コイン)で取れること、上限240分まで取れること、上限超え・30分刻みでない値・
0分が `INVALID_DURATION` で弾かれること、予約できる先が14日に延びていること
(8日先は通り、15日先は `START_TOO_FAR`)を確認します。

### `90_trial_discount.sql` について

ホストが自分で設定する初回お試し割引(0038)。割引価格で請求されること、
**手数料が割引後の金額にかかること**(定価にかかっていないこと)、2回目は定価に
戻ること、ホストに辞退された場合は初回扱いのままであること、**延長分は通常価格
になること**(0039)、最初から長めに予約したほうが安くなること、100%(無料)が
制約で弾かれることを確認します。

書いていて1つ危なかった点: フロント側の `setHostPref` は
`key === 'isHost' ? ... : ... : 'bio'` という三項演算子の連鎖で列名を
決めていたため、新しいキーを足すと**黙って bio 列を書き換える**状態でした。
対応表(`HOST_SETTING_COLUMN`)に変えています。

### `80_ranking_avatar.sql` について

「トップページのランキングにプロフィール写真が表示されない」不具合(0037)の
確認。`host_ranking()` が `avatar_initial`/`avatar_color` しか返しておらず
`avatar_path` を返していなかったため、実写真を設定していても頭文字+カラーの
プレースホルダーしか出せなかった。avatar_path を追加で返すよう修正している。

### `98_integrity_checks.sql` について

取引データの日次整合性チェック(0043)。前半は「実際のRPCだけで一通りの取引を
回したあと、全チェックが ok になるか」を見ます。ここが通ることで、0043 が
前提にしている不変条件

```
Σ coin_transactions.amount == balance + bonus_balance + earned_balance
```

が、0003〜0046 の実装に対して**本当に成り立っている**ことを確かめられます。
残高変動は必ず1行の履歴を伴うので、どのバケット(有償/ボーナス/報酬)に
入ったかを分類しなくても、合計だけで全てのズレを捕まえられるのが利点です。

後半は「わざと壊したときに検知できるか」。検知できない検知機能は無意味なので、
残高の直接書き換え・履歴1行の欠落・換金額の改変・失効処理の停止という
壊し方ごとに、**どのチェックが鳴るか**まで確認します。

### `99_ledger_immutable.sql` について

取引台帳の追記専用化(0044)。守りたいのは「うっかり」です。管理画面から行を
選んで消す、`where` を付け忘れた UPDATE を流す、退会処理のつもりで
`auth.users` を消す。これらが全部止まること、`remaining` の更新のような
通常運用の経路は塞がれていないこと、そして
`set local app.ledger_override = 'on'` を宣言したときだけ通り、
そのとき必ず旧値が `ledger_audit` に残ることを確かめます。

10番目が重要です。マネーテーブルは全て `auth.users` に `on delete cascade` で
ぶら下がっているため、これまでは**ユーザーを1行消すだけで入金記録も換金記録も
道連れ**になっていました。0044 以降はそこで止まります。

### `91_account_anonymize.sql` について

退会の匿名化(0046)。**退会させたあとも入金・換金の記録が残っているか**が本丸です
(テスト6)。あわせて、未処理の予約・処理待ちの換金・未払いの報酬が残っている
うちは実行できないこと、前払いコインの失効がロット・残高・履歴の3点セットで
行われ 0043 の照合が鳴らないこと(テスト8)を確認します。

### `30_cancellation_evidence.sql` の役割が変わりました

もともとは E-10(「開始1時間前まで全額」と表示しながら承諾の瞬間から全額没収
されていた問題)を**再現する**テストでしたが、0040 で直したので「直っている
ことを確かめる」内容に書き換えました。

このとき **0045 の不具合を1件見つけました**。0040 で立証材料ビューを作り直した際、
返還率の算出にキャンセル**後**の status をそのまま渡していたため、
`booking_refund_percent()` が「'confirmed' 以外は0」と判定し、
**全てのキャンセルが「返還0%」と記録されていました**。
消費者契約法9条の検討材料として弁護士に出すと事実と逆の説明をしてしまうため、
キャンセル直前の状態を `confirmed_at` の有無から復元して渡すよう直しています。

### `92_ledger_export.sql` について

R2への外部バックアップの鮮度チェック(0047)。バックアップの仕組みそのものより
**止まったことに気づけるか**のほうが大事なので、止まり方ごとに鳴るかを見ます。
一度も実行されていない / 差分が3時間止まった / 全量が26時間止まった / 実行は
したが失敗した、の4通りです。

8番目は 0047 で直した `integrity_latest` の定義の確認です。以前は
`ran_at = max(ran_at)` で「最後の実行」の行だけを出していたため、
**実行周期の違うチェックを足すと片方が消える**状態でした。
チェック名ごとの最新を出す形に変えています。

### `93_longer_play.sql` について

あそぶ時間の長時間化(0048。上限は0049で10時間に確定)。上限を上げること自体より、上げたときに壊れる
3点が直っているかが本題です。

いちばん重いのは**自動確定の起点**です。`auto_complete_bookings` は
`scheduled_at`(=開始時刻)+72時間を基準にしていたため、プレイ時間を延ばすと
猶予が縮み、さらに `extend_booking` には**総時間の上限が無かった**ので、
延長を重ねると**プレイ中に報酬が確定**しうる状態でした。
テスト8で「開始+73時間ではまだ確定せず、終了+72時間を過ぎたら確定する」ことを、
テスト9で延長の上限を確認しています。

次に**没収額の上限**(消費者契約法9条)。時給2,000円×10時間=20,000コインを
開始直前キャンセルで50%没収すると10,000円になり、「平均的な損害」として
説明が困難です。「経過した時間分 + 3時間分」を上限にしました。
テスト5が重要で、**4時間以下の予約では上限に届かず、従来と同じ額になる**ことを
確かめています(ここが変わると、説明済みのポリシーと食い違う)。
テスト6は開始後のケースで、既に提供された役務の対価はピタメイトのものとして
残ることを見ています(これを入れないと、10時間予約の9時間目にキャンセルされた
ピタメイトが3時間分しか受け取れません)。

### `94_slot_conflict.sql` について

予約時間帯の重複チェック(0049 / E-13)。`create_booking` には重複の検査が
まったく無く、同じピタメイトの同じ時間帯に何件でも予約が入る状態でした。
最長4時間のうちは衝突が稀で表面化しませんが、長時間の予約は1件で1日の枠の
大半を占めるため、放置できません。

設計で一度つまずいた点があります。当初は承諾のときも「申請中」の予約を
ふさがっていると見ていたのですが、それだと**同じ枠に2件のリクエストが並ぶと
ピタメイトがどちらも承諾できなくなります**(テスト7で発覚)。申請は希望であって
確約ではないので、承諾と延長は**成立済みだけ**を見るように分けました。
新規の申し込みでは申請中も枠として扱います(コインは申込時点で確保されており、
先に申し込んだ人の枠を守るべきなので)。

テスト12は「今すぐ」の申し込みの扱いです。`requested_start_at` が null の場合は
`scheduled_at`(=作成時刻)を開始と見なすため、二重の「今すぐ」申し込みも弾かれます。

### `89_no_show_auto.sql` について

無断欠席の自動処理(0050)。ねらいは**運営が判断しないこと**なので、
「ゲストの申告では何も確定せず、ピタメイトの不作為だけが結果を決める」ことを
重点的に見ます。

テスト2が要です。ゲストが「はじめました」を押しても、その瞬間には保留も確定も
起きません。押して起きるのは、開始+15分の自動判定の**対象になること**だけです。
ここで即返金にすると「無料キャンセルの抜け道」になります。

テスト8は押し忘れの救済で、**メッセージ1通でチェックイン扱いになり保留が解ける**
ことを確認します。Discordに移って遊ぶケースがあるため、ボタンだけを条件にすると
実際に参加しているピタメイトが不当に無断欠席にされます。

テスト11は逆向きの安全弁で、ゲストのチェックインが無ければこの仕組みは
一切発動しないことを見ています。

### `88_host_availability.sql` について

ピタメイトの募集枠と公開スケジュール(0051)。これまで「いつ遊べるのか」を表す
情報がどこにも無く、空いている時間が「募集しているから空いている」のか
「そもそも出ていない」のか区別できませんでした。ゲストからは、深夜3時に
申し込んでよいのか分かりません。

いちばん気をつけたのは**枠を設定していないピタメイトを締め出さないこと**です
(テスト1・8)。いきなり予約不可にすると、既存のピタメイトが黙って消えます。
「1枠でも設定したら、その枠の中だけ」という形にして、設定しない人は従来どおりに
しています。

テスト7は、プレイ時間の**全体**が枠に収まっている必要があることの確認です。
開始時刻だけを見ると、22時から2時間の予約が23時台(閉じている)にはみ出します。

曜日・時は日本時間で解釈します(テスト4)。サーバのタイムゾーンがUTCでも
利用者の感覚とずれないようにするためです。
